== User identity through Spark Connect

[.kicker]
Proof of concept

[.lead]
Secure propagation of user identity and end-to-end session correlation.

[.notes]
****
This PoC works and runs today. A user signs in, and their identity goes through Spark Connect to the Polaris catalog and then to temporary credentials on object storage.
Spark itself has no object-storage credentials.
Everything here is tested against a running stack: 43 end-to-end checks and 109 unit tests.
It takes about thirty minutes. The last third covers what we found out about the upstream projects.
****

== The problem

image::{diagrams}/ambient.svg["Who reads the data: as shipped, and with this PoC",opts=inline,role=diagram]

[.notes]
****
Out of the box, Spark Connect has at most a shared secret for the channel. The `user_id` is whatever string the client sends.
So the catalog and the object store only ever see Spark, which uses one service credential and one static key that can read every table.
If you ask the audit log who read the salaries, it says "spark".

Click. With the PoC, each caller sends its own token.
The server checks it, sets `user_id` from it, and exchanges it for a token issued for Polaris.
Polaris authorises that user and gives back a key that only works on one table's files and expires after a few minutes.
Now the audit log says "alice".
****

The only fork is of Ontop, for the SPARQL endpoint. We'll get to why.

== The stack

image::{diagrams}/stack.svg["The stack",opts=inline,role=diagram]

[.notes]
****
It all runs in Docker Compose: Keycloak 26.7, Polaris 1.7, MinIO, Spark 4.1.3 with a standalone master and worker, Marquez, Ontop and the two consoles.
We need a real worker JVM. With `local[*]` the executors are threads inside the driver, so a successful read wouldn't tell us anything about the workers.

The plugin has three parts: an interceptor on the gRPC server, a static identity holder, and an Iceberg AuthManager.
The jar goes into Spark's own jars directory instead of `--jars`. With `--jars` it lands in a child classloader, the interceptor and the AuthManager each get their own copy of the static holder, and the token disappears without an error.

Click. The other callers: Ontop runs SPARQL queries as the caller, the Polaris console shows each user their own catalog, and lineage goes to Marquez.
****

== The path of a query

image::{diagrams}/query-path.svg["The path a query takes",opts=inline,role=diagram]

[.notes]
****
The server is drawn as two lifelines, one per thread, because getting from one thread to the other is the hard part.

. The client sends ExecutePlan with the token and correlation ID as gRPC metadata. It also sends an operation id that it generated.
. On the gRPC thread, the server validates the JWT against a cached JWKS. It checks that the `user_id` in the request is the token's subject, and that the subject owns the session.
. It exchanges the token at Keycloak for one issued for Polaris, then stores the identity.
. Spark runs the operation on a new thread. The only thing that comes across from the gRPC thread is the job tag.
. The AuthManager reads the tag, looks up the identity and calls Polaris as alice, with her correlation ID in `X-Request-ID`.
. Polaris returns the table metadata and a scoped key. The worker reads from MinIO using that key.
****

****
This is the Python client's interceptor. It only uses public PySpark API: a custom channel builder and `add_interceptor`.

The token is read on every call, so if the provider refreshes it, a long session keeps working.
It goes in its own header, `x-user-token`. Spark's pre-shared-key interceptor already uses `Authorization` to decide whether the client is trusted at all. The user token says which user it is, and both checks run.
We use metadata because Spark writes the whole request proto into the job description. A token in the request body would show up in the Spark UI.
****

== Hop 2: token exchange

image::{diagrams}/token-exchange.svg["RFC 8693 token exchange",opts=inline,role=diagram]

[.notes]
****
The server doesn't pass the user's token on.
It's a confidential Keycloak client, and it asks Keycloak for a token issued for Polaris on alice's behalf. This is standard token exchange (RFC 8693), which Keycloak 26.7 has on by default.

The new token has the same subject but a different audience and authorised party. It also carries the claims Polaris reads, `principal_name` and `principal_roles`.
Polaris looks the principal up by name, so Keycloak doesn't need to know Polaris's internal ids.

Exchanges are cached by a hash of the inbound token. Validation uses a cached JWKS, so in the normal case neither step makes a network call.

One thing that cost us time: `audience=polaris` doesn't add an audience. It only filters the ones a mapper has already added. It's in the findings.
****

== Hop 3: crossing threads

[.lead]
Spark runs each operation on a new thread that isn't from a pool. The job tag is the only thing that comes with it.

image::{diagrams}/thread-bridge.svg["Crossing the thread boundary with the job tag",opts=inline,role=diagram]

[.notes]
****
This is the hardest part of the design.

The interceptor runs on the gRPC handler thread. It stores the identity in a static holder, keyed by operation and by session.

Click. None of the thread-local state reaches the code that calls Polaris. That includes ThreadLocals, the gRPC Context and the MDC. `ExecuteThreadRunner` starts a new thread for every operation, on purpose.

Click. What does reach it is the job tag that Spark sets inside `withSession`. It contains the user, the session and the operation.

Click. The AuthManager reads the tag from its own thread and looks up the identity.
The tag format is internal to Spark, so this is the one part of the design that could break on an upgrade.
The `Operation_` part only works because our clients set `operation_id`. PySpark leaves that to the server, which never tells the client what it picked.
****

== Hop 4: Polaris authorises and hands out keys

image::{diagrams}/vending.svg["Per-caller credentials, vended by Polaris",opts=inline,role=diagram]

[.notes]
****
Polaris authorises the principal named in the token, using the roles in it. alice is a data engineer and can use the whole catalog. bob is an analyst and can only read the shared namespace.

When Polaris allows a table load, it gets a temporary key from STS with a session policy limited to that table's prefix.
alice and bob get different keys, and neither one is the MinIO root key. MinIO's audit log shows what the executor sent: a temporary key with parent `minio_root` and a session policy.

When Polaris refuses, there's no key. Spark containers have no S3 credentials, so if a read works, it used a key issued for that caller.
****

== Session hijacking

image::{diagrams}/hijack.svg["Claiming another user's session",opts=inline,role=diagram]

[.notes]
****
This is the most serious finding.
Spark Connect identifies a session by `(user_id, session_id)`, and both come from the request. `user_id` is from the connection string or `$USER`, and the client generates the session id.
Neither is tied to an authenticated identity. The shared secret can't help, because every client sends the same one.

Click. On a shared server, anyone who can connect can name another user's session and attach to it. They get that user's temp views, cached DataFrames and UDFs, and in this setup, their credential as well.

Click. The interceptor rejects the request before Spark sees it. `test_bob_cannot_claim_alices_session` tries the attack and gets PERMISSION_DENIED.
If you run Spark Connect for more than one user, you have to fix this yourself.
****

== One correlation ID across services

image::{diagrams}/correlation.svg["One correlation ID, everywhere",opts=inline,role=diagram]

[.notes]
****
The client generates a UUID. In Python it lasts for a `with correlation_id()` block, in Java for a scope, and in Rust for a session.
It goes over gRPC as metadata. The AuthManager sends it to Polaris as `X-Request-ID`, which Polaris already writes into its MDC and audit events.
The Spark log format copies Polaris's `[requestId,realm]` layout, so the lines are easy to compare.

The correlation ID and the operation id are separate. One `collect()` makes two ExecutePlan calls, a block can run many statements, and Spark rejects a repeated operation id. The server logs both ids together.

`make cid` searches every service's logs for one ID.
****

[.lead]
The server doesn't change between clients. It's the same build and config, and it receives the same headers.

[.notes]
****
All three clients share one token cache, so after you sign in with one you're signed in for the others.

Python needs one private hook. PySpark never sets `operation_id`, so the client patches that private method on its own instance only.
The JVM client only uses public API. Its jar moves gRPC to a different package than the server's jar does, so client and server interceptors can't share a type. It also needs `--add-opens` for Arrow.
Rust didn't need anything for `operation_id`. It's also the only client that can't scope a correlation ID to a block, because the crate fixes a session's headers when the session is created.
****

== Jobs with no user

* All three clients have a `ClientCredentialsTokenProvider` for jobs that hold a client id and secret
* Keycloak issues the token to `service-account-spark-job`. Nothing after the client changes
* Polaris checks that account's own grants. It can read `shared` and gets a 403 on `restricted`, like bob
* Polaris has to know about the service account in advance, the same as any other principal
* There's no refresh token and nothing is written to disk. When the token goes stale, the client runs the grant again

[.notes]
****
People usually ask about this: what about jobs that run unattended?
They take the same path. The subject is the service account. The server pins `user_id` to it and exchanges the token, and Polaris authorises it by name.

All three clients use `client_secret_basic` and form-urlencode each half before base64, as RFC 6749 says. Rust's reqwest `basic_auth` skips that step. It works until a secret contains a `%` or a `+`.
****

== The same identity in SPARQL

image::{diagrams}/sparql.svg["The same identity, through a SPARQL endpoint",opts=inline,role=diagram]

[.notes]
****
Ontop is a virtual knowledge graph. It turns SPARQL into SQL over the same Iceberg tables and runs it through Spark Connect's JDBC driver.

Ontop already knows who sent the query, but it had no way to pass that on. Its connection pool is shared by the whole process and built once from a single JDBC URL, so every SPARQL query reached Spark as the endpoint.
The fork (larsw/ontop, branch version5-auth-context) adds three opt-in changes. The query context is available when a connection is acquired, a new pool builds each request's JDBC URL from it, and Ontop uses the caller's correlation ID as its query id.
On our side, the Spark Connect JDBC driver turns URL parameters it doesn't know into gRPC metadata, which is where the plugin reads them.

The endpoint has no credentials for the data. The table definitions it needs are in a file, so it never has to sign in as anyone.

Click. alice and bob send the same query to the same endpoint, and Polaris refuses bob.
The browser console at localhost:3002 shows the same thing.
****

== Lineage

image::{diagrams}/lineage.svg["Where per-user catalog auth and lineage collide",opts=inline,role=diagram]

[.notes]
****
OpenLineage runs as a normal SparkListener, so job-level lineage works: each test run produces eight jobs in Marquez.

Click. Dataset-level lineage doesn't work. To name a dataset, OpenLineage loads the table from the catalog on the listener bus thread. That thread has no job tag, so the AuthManager has no identity and sends the call without a token, and Polaris returns 401.
It's the same thread problem as before. If the catalog authorises each user, only a user can read it, and the lineage collector isn't one.

Click. The job-start event does carry the tags, though, so each job-backed run gets a facet with the correlation ID and principal. That's enough to record who ran it, but not to call the catalog.

We see three fixes. We could give the collector a service identity, but that brings back the shared credential the PoC removes. We could resolve datasets from the query plan. Or we could pass the identity to the listener, keyed by run. Only the last one keeps both per-user access and dataset lineage.
****

== What we found upstream

[cols="1,9",options=header]
|===
|§ |Finding

|1
|Spark Connect relocates gRPC, but its docs name the original interface

|3
|Spark Connect doesn't tie a session to the authenticated caller

|4
|Job tags are the only public way across the thread boundary, and their format is internal

|5
|PySpark never sets `operation_id`, and one statement can be several operations

|9
|RFC 8693 `audience` filters audiences but doesn't add them

|14
|PySpark's session finaliser can deadlock against gRPC, in about one run in four

|15
|Per-user catalog authorisation conflicts with out-of-band lineage collection
|===

[.source]
Each finding was checked against source code, published jars or the running stack. Details in FINDINGS.md. Versions: Spark 4.1.3, Iceberg 1.11.0, Polaris 1.7.0, Keycloak 26.7.0.

[.notes]
****
FINDINGS.md has seventeen of these, with the evidence for each. Two that aren't on the slide: §6, `UserContext.extensions` works but whatever you put in it shows up in the Spark UI, and §16, Ontop couldn't pass the caller to the database, which the SPARQL slide covered.

Some stories behind the ones listed:

§1: The docs say to implement `io.grpc.ServerInterceptor`, but the jar doesn't contain `io.grpc` at all. It's been moved to `org.sparkproject.connect.grpc`. Code written against the docs compiles and then fails when the server starts.

§14 looked like a flaky test for an afternoon. The session finaliser shuts down a thread pool shared by the whole class and waits for it. If the garbage collector runs the finaliser while you're in a gRPC call, the process hangs. Stopping sessions explicitly made the hang rarer, which was worse, because it looked fixed. Keeping the sessions alive until exit fixed it, and we got 45 clean runs.

We think several of these should be reported upstream, starting with §1 and §3.
****

== Not in scope

* TLS between the client and the Connect server
* A token expiring in the middle of a long query
* Polaris persistence: it's in memory and is set up again on every restart
* Secrets management: all the credentials in the sandbox are throwaway
* Dataset-level lineage, which needs the identity passed to the listener as well

[.notes]
****
We left these out on purpose. TODO.md records the twenty-three design decisions and the reason for each one. Several were forced by how the upstream projects behave.
The lineage gap has the most interesting fix, because it's the same job-tag approach used one thread further along.
